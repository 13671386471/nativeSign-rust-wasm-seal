## 关键教训
- **`cargo check` 不等于 `cargo build`**：wasm-bindgen 的 `export_name` 重复符号冲突只在 LLVM codegen 阶段报错，
  check 通过但 build 失败。验证 wasm 产物必须跑一次 `cargo build --target wasm32-unknown-unknown`（或 wasm-pack）。
- `Blob` 序列构造函数（`new_with_u8_slice_sequence` 等）在本机 web-sys 0.3.103 真实签名是 `&JsValue`，
  需手动用 `js_sys::Array` + `unchecked_into::<JsValue>()` 构造，而非直觉的 `&[&[u8]]`。
- `js_sys::JsValue` 不可作为路径访问（js_sys 内部 `use wasm_bindgen::prelude::*` 是私有再导出），直接用 `wasm_bindgen::JsValue`。

### ⚠️ 启动期崩溃根因：wasm 二进制缓存未清除导致"新 JS + 旧 wasm"版本错配
- 现象：`[boot] PDFium 模块绑定失败` + `RuntimeError: unreachable`（wasm 内回调 trampoline）。
- 根因：`index.html` 用 `?v=Date.now()` 给 **JS glue** 清了缓存，但 `pkg/dianju_wasm_seal.js`
  的 `__wbg_init` 在未传参时用 `new URL('dianju_wasm_seal_bg.wasm', import.meta.url)` 加载 wasm，
  **不带任何 cacheBuster** → 浏览器命中 7 月的旧 wasm 缓存，新 JS 胶水层与旧 wasm ABI 不匹配
  → `initialize_pdfium_render` 返回 false，后续回调 trap `unreachable`。
  （无头全新 profile 无缓存，因此我这边首次复现是"绑定成功"，反证是缓存问题。）
- 修复：`await wasmBindings.default({ module_or_path: './pkg/dianju_wasm_seal_bg.wasm' + cacheBuster })`
  强制 wasm 与 JS 同 cacheBuster。注意：直接传字符串会触发 wasm-bindgen 的 deprecated 警告，
  用对象形式 `{ module_or_path: ... }` 无警告。
- 复现/回归脚本：`test/cdp.mjs`（复制自 headless-browser-verify 技能）+ `test/repro-boot.mjs`
  （抓启动控制台）+ `test/verify-seal-click.mjs`（落章点击断言）。

### 关键教训
- wasm-bindgen web 产物的 wasm 二进制默认 URL 不继承 JS 的 `?v=`，**必须显式给 wasm 也加 cacheBuster**，
  否则"热更 JS 但缓存旧 wasm"必然 ABI 错配崩溃。
- `bind_to_pdfium` 的成败只取决于 PDFium 模块（`_malloc/_free/ccall/HEAPU8/函数表`），与本项目 Rust 源码无关；
  遇到"绑定失败"应先怀疑 PDFium 模块加载/cache，而非命中测试等业务代码。

## 2026-10-19 下午 — 修复"已签 PDF 打开后印章处多出红圈/hex 串/绿勾"

### 现象
加载 OpenSign 已签的劳动合同 PDF（有 6 个 `/Widget /Sig` 签章注释），未做任何点击前，
印章位置多出：红色圆圈 + 一串 32 位 hex 文本（如 `066894f237e64e1799a169fc5e96297d`、`fbf8bb42610c...`）+ 绿色 ✓。
参考渲染（PyMuPDF `get_pixmap` 含注释 / 标准查看器）是干净的。

### 根因（双层渲染叠加）
- PDF 页内容流里**没有**红/图（无 `1 0 0 rg`、无 `/Im`），印章只在 6 个 Sig 注释的 `/AP /N` 外观流里（`/Im1 Do`，就是印章图片）。
- PDFium 渲染配置 `.render_form_data(true)` 已经把注释外观渲染出来了（真印章可见）。
- 但 `render.rs::render_page_to_canvas`（PDF 路径）在 `put_image_data` 之后**又遍历 `doc_state.seals` 调 `render_seal()` 叠加**。
- `engine.rs::parse_existing_signatures` 对解析出的已有签章设 `origin:"pdf"`、`seal_image:""`、`seal_name=field_name`（= 注释 `/T`，OpenSign 用的就是 32 位 hex UUID）、`signed:true`。
- `render_seal()` 因 `seal_image` 为空走**回退分支**：画 `#D81E06` 红圈 + 红字 `seal_name`(那串 hex) + `signed` 时画 `#52C41A` 绿 ✓。
- 于是"PDFium 真印章 + 我们的红圈/hex/绿勾"重叠 → 用户看到的"多出来的红圈和一串内容"。

### 修复
`render.rs` PDF 渲染路径的印章叠加加条件：`seal.seal_info.origin != "pdf"` 才 `render_seal()`。
- 已存在于 PDF 的签章（origin=="pdf"）交给 PDFium 注释层渲染，不再叠加；
- 仅叠加本会话新添加、尚未嵌入 PDF 的印章（origin=="local"），回退红圈/名称/勾仅用于新章预览。
- OFD 路径（`render_seal_ofd`）不动：OFD 由自有渲染器绘制页面内容，Sign 对象需叠加。

### 验证（无头 Chrome + CDP，真实 OpenSign 文件）
- 修复后渲染：红圈/hex/绿勾全部消失，只剩 PDFium 渲染的两枚真实印章（与 PyMuPDF 参考一致）。
- 点击高亮仍正常：`HitTestSeal` 命中=true；点已有印章→`#sealSelectionBox` display:block 120×119.857px、top≈54.9（印章 y=55 正确）；点空白→none。

### 关键教训
- **PDFium 已渲染注释时，切勿再对同一批 seal 叠加自有外观**，否则双层重影。
  判别用 `seal_info.origin`（"pdf"=文件内已有，"local"=本会话新加）。
- 调试这类"多出内容"先用 PyMuPDF 做参考渲染对比，再二分：查页内容流 / 注释外观 / 渲染层叠加 三层。

## 参考实现调研：原 C++/Qt 阅读器的"选中印章红框"怎么来的
原项目 `D:\workspace\front-new\dianju-ui-admin`：
- 阅读器是 **Qt for WebAssembly 单 canvas**：`public/wasm/qtloader.js` + `dianjureader.wasm`(31MB，源码编译，无 JS 逻辑)，
  `dianjureader.js` 里 `getContext('2d')`；工具栏(打开/查找/放大…)+文档全画在同一个 canvas 内。
- 前端只做接线：`src/views/wasmSeal/index.vue` 动态 `<script>` 加载 dianjureader.js/qtloader.js/ofdwebsdk/*.js，
  调用 `OFD_Plugin._IniCtrlReadytCallback / registListener("tool_selectpoint"/"pageindex") / SetValue / SelectPoint`；
  **不创建任何 canvas / DOM 覆盖层**。
- `public/wasm/ofdwebsdk/*.js` 只封装 init(spinner/screen/status) 与控制台日志，**无任何 strokeRect/红色画框代码**（grep 0 命中）。
- 结论：红框是 **Qt C++(QPainter) 画进 canvas** 的选中态——鼠标命中注释 `/Rect` → 重绘并在边界画红色空心矩形；点空白清除。
  与本项目 `rust-wasm-seal` 用 DOM 覆盖层 `#sealSelectionBox` 实现的效果等价，只是"画在 canvas 像素层" vs "画在 DOM 层"。
- 该 PDF 的 `/Widget /Sig` 注释 `/Border`/`/BS`/`/MK` 全为 None，PDF 里本就没有边框数据，一切选中框都是阅读器 UI。

## 2026-10-19 下午 — 文本搜索(search_text)验证 + 两个字节切片 panic 修复

### 背景
用户指出搜索功能"没有 UI 入口"。核查：Rust `search_text` 与 `ofd_plugin.js::SearchText` 都在，
但 `index.html` 无入口；且实测搜索会触发 wasm panic（并非慢）。

### 新增搜索 UI 入口 (index.html)
- 工具栏加 `.search-box`（`#searchInput` + `#searchBtn` + `#searchSummary`）+ `#searchResults` 结果面板。
- `doSearch()` 调 `plugin.SearchText(q,0,0)`，解析 `{found,total,matches:[{page,count,snippet}]}`，
  渲染"共 N 处 / M 页"、逐页结果；点结果 `scrollToPage(page-1,true)` 跳页。
- `bindSearchUI()` 在 `window._onEngineReady` 中调用；回车触发。函数在 classic script(725-1551) 内（与 getPlugin/scrollToPage 同域）。

### 修复 1：make_snippet 字节切片 panic（engine.rs）
- `engine.rs::make_snippet` 旧实现 `&text[start..end]` 用字节索引，中文多字节 → "byte index not a char boundary" panic
  → wasm abort → Promise 永不 resolve（表现为 CDP 180s 超时）。搜索对中文**必然崩溃**。
- 改为按 `chars()` 截断：先把字节位置转字符数（并 is_char_boundary 校正），再用 `chars().skip().take()` 取片段。

### 修复 2：OFD 渲染调试日志字节截断 panic（render.rs:633）
- `render.rs::render_ofd_text` 调试日志 `&text_preview[..15]` 按字节截断，OFD 中文文本第一段即 panic
  (`end byte index 15 is not a char boundary; inside '则'`) → OFD 加载/渲染整体 abort（连带 `RefCell already borrowed`)。
- 改为 `let preview: String = text_preview.chars().take(15).collect();`。
- 排查确认其余切片（`&data[0..8]`、`&idat_data[..]`、`image_data[..]` 等）均作用于 `Vec<u8>`/ASCII 路径，安全。

### 优化：搜索用原始字节（避免解析超大预处理 PDF）
- 现象：`search_text` PDF 分支原本**每页** `lopdf::Document::load_mem(&raw_data)`；raw_data 是字体嵌入后 8.7MB →
  解析极慢。且 `DocState` 只有 raw_data。
- 改：`DocState` 新增 `original_data: Vec<u8>`；`load_file` 在预处理与原始字节长度不同(即真做了嵌入)时保存原始字节。
  `search_text` 优先用 `original_data`（96KB、自带 ToUnicode），否则回退 raw_data；PDF 只 `load_mem` 一次（提到循环外）。
- 原始 `test_labor_contract.pdf` 两个字体都有 `/ToUnicode`，pypdf/lopdf 均可正确抽出"楚红"，故搜索用原始字节既快又准。
